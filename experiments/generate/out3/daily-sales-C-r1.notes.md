**1. 最初の仮説**
- 運用や経理の人が、毎朝 cron で「日本時間の前日」の売上（件数と金額）を JSON で受け取れるようになる。アプリに注文を読み込まず、SQL で集計する（commits.txt）。

**2. 変更前のコードが守っている約束（base）**
- `updated_at` は `this.#now().toISOString()` で保存されている。つまり **UTC の ISO 文字列（`...Z`）** になる（`src/orders/sqliteOrderRepository.ts:51`）。スキーマでは TEXT 型で、タイムゾーンの決まりは書かれていない（`db/migrations/001_create_orders.sql:8`）。
- 金額は円の整数で持ち、負の値は CHECK で弾く（migration:4-5）。status は CHECK で 4 つの値に限られる（:6）。
- 索引 `(status, updated_at)` は照合バッチのために作られた（migration:11-12）。
- PAID のあとに注文を更新する経路はない。checkout は CART と PAYMENT_FAILED しか受け付けず（`orderService.ts:33`）、照合バッチは PENDING_PAYMENT しか触らない（`reconcilePendingPayments.ts:17-20`）。これは型や DB の制約ではなく、**手順で守られている**。
- 照合バッチで PAID になった注文の `updated_at` は、バッチが動いた時刻になる（作られてから 10 分以上あと）（reconcile:6, 25, 31。save が now を入れる）。
- `openDatabase` はファイルがなくても作り、マイグレーションを当てる（`db.ts:8-27`）。

**3. 変更との突き合わせ**
- `salesOn` は `${date}T00:00:00` から翌日 0 時までの範囲で文字列を比べている（head `dailySales.ts:61`）。保存されているのは UTC なので、「日」は **UTC の暦日**（日本時間の 09:00〜翌 09:00）になる。
- 一方、CLI の既定の日付は **日本時間の昨日**（`printDailySales.ts:8-12`）。2 つのファイルで「日」の意味がずれている。
- テストはすべて `03:00Z`（日本時間 12:00）の注文を使っている。UTC の日付と日本時間の日付が同じになる時刻なので、ずれを捕まえられない（`test/dailySales.test.ts:23-50`）。

**4. 8 つの分野**
1. 約束: **兆しあり**。時刻の前提（UTC と JST）が食い違っている。PAID は不変という前提が、手順でしか守られていない。
2. 失敗: 兆しあり（小）。DB のパスが違うと空の DB が作られ、0 件 0 円が正常終了で出る（`db.ts:9`、`printDailySales.ts:26`）。
3. 出したあと: 読み取り専用で、新しい CLI なので戻せる。ただし数字は人が読む。cron が毎朝 7 時に走ると、取りこぼしが静かに起きる。
4. 信頼の境界: 十分。引数は `parseReportDate` で検証し、SQL にはバインドで渡している（`dailySales.ts:23-30, 61`）。
5. 規模: 十分。集計 1 回で、索引の範囲を使う（索引が使われるかは推測）。
6. 次に変える人: 兆しあり（中）。「日本時間で区切る」という決まりが CLI 側にしかない。分けた設計そのものは良い。
7. テスト: **兆しあり**。肝心の境界を壊しても、どのテストも落ちない。
8. AI 特有: `import.meta.main` は Node のバージョンによっては無いかもしれない（リポジトリの外のことなので確かめられない。README は 23.6 以降としている）。頼まれていない抽象はない。

**5. 選んだ分野**
- 1（時刻）と 7（テスト）を厚く語る。売上の数字が日ごとに静かにずれ、取りこぼしも起き、テストは緑のままになるから。
- 次に 1 の「PAID は不変」と 2 の空 DB を語る。
- 気にしなくてよいもの: SQL インジェクション、規模、ISO 文字列の比べ方、注文 0 件のときの COALESCE、OrderRepository と分けたこと。
- 良い点: 実在しない日付の検証、集計を SQL に任せたこと、yesterdayInTokyo を日本時間で決めたこととそのテスト。
