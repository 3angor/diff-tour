**1. 最初の仮説**
- 経理と問い合わせ対応の人が、期間内の注文を CSV で見られるようにする変更。管理者だけが呼べる GET の API を足し、照合バッチと同じリポジトリのメソッドを広げて使っている（commits.txt）。

**2. 変更前のコードが守っている約束（base）**
- `updated_at` は「最後に save した時刻」。`save` のたびに `now()` で書き換わる（base/src/orders/sqliteOrderRepository.ts:51、orderRepository.ts:24）。「注文した日」や「支払った日」を表す列はない（base/db/migrations/001_create_orders.sql:1-9）。
- `findByStatusUpdatedBefore` の呼び出し元は照合バッチだけ（base/src/jobs/reconcilePendingPayments.ts:17-20）。索引 `(status, updated_at)` はこのバッチのためのもの（migration:11-12）。
- 決済が途中で止まった注文は、照合バッチがあとで PAID か PAYMENT_FAILED に直す（orderService.ts:56-58）。そのたびに `updated_at` が進む。
- app.ts は環境変数に、そのまま動く既定値を入れている（`?? 'test-key'` など。base/src/app.ts:7-12）。ないときに止める仕組みはない。
- 金額は円の整数で持つ（migration:4-5）。照合のキーは `paymentKeyFor` だけで作る（order.ts:13-19）。

**3〜4. 8 つの分野を当てた結果**
1. 約束：兆しあり。`updated_at` の意味が、経理が月で区切るのに使えるか分からない。照合バッチの SQL の意味は変わっていない（確かめた）。
2. 失敗：兆しあり。`ADMIN_TOKEN` が未設定だと、`undefined !== undefined` が false になり、認証が通る側に倒れる（head/src/handlers/orderExport.ts:26、app.ts:15）。読み取りだけなので、エラーで途中の状態が残ることはない。
3. 出したあと：十分な場合に当たる。マイグレーションはなく、読み取りだけで、すぐ戻せる。ただし誰が書き出したかのログはない。
4. 信頼の境界：兆しあり。上の 2 と同じ。比較が timing-safe でない（軽い）。filename に入る値と SQL の組み立ては安全（確かめた）。
5. 規模：軽い兆し。状態を指定しないと索引の先頭列を使えず、全件を走査すると推測する。上限がなく、全部をメモリに載せる。
6. 次に変える人：兆しあり。名前が「Before」なのに範囲検索に使い、呼び出しは `(null, range.to, range.from)` と並びが逆になる。共通の関数に呼び出し元ごとの分岐が増えた。
7. テスト：兆しあり。カンマのテストは、期待値を本体と同じ `toCsvRow` で作っている。トークン未設定のテストもない。
8. AI 特有：軽い兆し。`URL.parse` はリポジトリの外の Node API で、ここでは確かめられない（README は Node 23.6 以降を求めている）。頼まれていない変更は混ざっていない。

**5. 見つけたこと**
- 必須：`ADMIN_TOKEN` が未設定だと、ヘッダーなしで全注文を取れる（handler:26、app.ts:15。テストの setup は常に 'secret' なので捕まらない。test/orderExportHandler.test.ts:9）。
  - 直し方：handler で `!deps.adminToken` なら 401 を返す。値で確かめた：(undefined, undefined)→401、('', '')→401、('secret', 'secret')→通る。
  - 起動時に止める案は、注文確定の API まで道連れにするので、handler で拒む方を推す。
  - timingSafeEqual に変えるなら、長さが違うと例外になり 500 で返る。閉じる側には倒れるが、先に長さを比べる。
- 問い（重い）：`updated_at` で月を区切ると、月をまたいで照合バッチが直した注文や、あとで払い直した注文が、前の月から消えて次の月に移る。経理の月次の突き合わせに使えるかを確かめる。直すならスキーマの変更が要る。
- 提案：範囲の検索用に専用のメソッドを分ける（`findUpdatedBetween(from, to)`）。
- 提案：カンマのテストの期待値を、文字列で直接書く。
- 提案（軽い）：timing-safe な比較にする。書き出しの監査ログを出す。
- Nit：CSV を Excel で開いたときの式の注入。customerId の出どころは、このリポジトリにはない。
- Nit：BOM がない。
- Nit：InMemory は並べ替えず、入れた順に返す。
- 気にしなくてよい：
  - SQL を文字列で組み立てているが、組み立てるのは固定の文字列だけで、値は全部バインドしている。
  - filename に入る値は正規表現を通ったあとのもの。
  - 日本は夏時間がないので、+09:00 に固定してよい。
  - ISO の文字列どうしの比較は、全部 Z 形式なので正しい。
- 良い点：
  - 日付を一度戻して、実在する日付かを確かめている。
  - 範囲を半開区間（from 以上 to 未満）にしている。
  - 境界の値を、前後 1 秒ずつテストしている。
  - 照合バッチの意味を変えていない。

**6. 手順を厚く使うもの**
- 認証が通る側に倒れること：お金ではないが、顧客と決済のデータが外に漏れ、戻せない。
- `updated_at` の意味：この変更の目的そのものに関わる。
- 共通化と名前：次に変える人が引っかかる。
- テストが何も証明していないこと：ジュニアが見落としやすい。
