**1. 最初の仮説**
- 決済の応答がタイムアウトした注文は、照合バッチが拾うまで最大 15 分ほど「決済中」のまま残っていた。この変更で、決済サービスから課金成功の通知が来た時点ですぐ PAID になり、利用者が待たなくて済むようになる。
- 仮説：「Webhook は成功だけを早める近道で、失敗の判断はこれまでどおり照合バッチが持つ」。

**2. 変更前のコードが守っている約束（base）**
- `PENDING_PAYMENT` は「課金されたか分からない」という意味。障害やタイムアウトでは状態を変えず、照合バッチに判断を任せる（`src/orders/orderService.ts:56-58`）。
- 照合バッチは、10 分より古い PENDING を決済サービスの記録と照らし合わせ、記録がなければ PAYMENT_FAILED にする（`src/jobs/reconcilePendingPayments.ts:5-6, 22-31`）。課金の有無を決めるのはこのバッチだけ。
- 冪等キーは `paymentKeyFor` で必ず作る（`src/orders/order.ts:13-19`）。テストは `order-o1` という形を固定している（`test/orderService.test.ts:23-27`）。
- 注文の保存は、読んで書き換えてから行全体を upsert する手順で行う。状態の遷移は DB の制約ではなく、アプリの手順で守っている（`src/orders/sqliteOrderRepository.ts:39-52`）。DB は同期の SQLite で、プロセスは 1 つ（`server.ts` の中で setInterval でバッチを回している）。
- マイグレーションは起動時に番号順で当てる（`src/db.ts:15-26`）。

**3〜4. 変更との突き合わせと、8 分野の確認**
1. **約束**：兆しなし（十分な場合に当たる）。遷移は PENDING→PAID だけで、失敗はバッチに任せている（head `paymentWebhook.ts:56-57, 73-78`）。`paymentKeyFor` の出力も変わっていない。
2. **失敗**：兆しあり → 確かめた結果、問題なし。注文を更新してから記録する順番で、途中で落ちても送り直しで済む（`paymentWebhook.ts:59-60`、テストは `test/paymentWebhook.test.ts:89-104`）。
3. **出したあと**：兆しあり（軽い）。
   - PAYMENT_FAILED の注文に課金成功が届いても `console.warn` だけで、処理済みとして記録される。誰も気付かないおそれがある。
   - テーブルを足すだけなので戻せる。鍵を設定しないと 503 を返す。
4. **信頼の境界**：十分な場合に当たる。鍵がなければ 503、署名は生の本文で確かめ、比較は定数時間、5 分を超えたものは弾く。注文の特定には、署名で守られた idempotency_key を使っている。
5. **規模**：兆しなし。1 イベントにつき行が 1 つ増えるだけ。ただし消す仕組みはない（Nit）。
6. **次に変える人**：
   - `orderIdFromPaymentKey` を `paymentKeyFor` の隣に置いたのは良い。
   - `record()` の戻り値が使われていない（Nit）。
   - 注文 ID の逆引きとイベント記録のテストが `webhookSignature.test.ts` に入っている（Nit）。
7. **テスト**：
   - 署名は openssl で作った固定値と比べているので良い。
   - 記録の順番を入れ替える壊し方、状態の確認を消す壊し方は、どちらもテストが捕まえる。
   - `server.ts` の経路（本文の読み込みと 413）はテストされていない。
8. **AI のコード特有の点**：
   - `timingSafeEqual` と `node:sqlite` の `changes` は Node の機能で、リポジトリの外のものなので確かめられない。
   - イベント表は、状態の確認に対する二重の防御になっていて、やりすぎではない。

**5. 指摘と重さ**
- **問い/提案**：PAYMENT_FAILED と課金成功の食い違いを warn だけで流している。500 を返して送り直させるのは直し方として不適切（何度送り直されても結果は変わらない）。記録したうえで、検知できるログや警報にするのがよい。
- **問い**：
  - 中身の不正な charge.succeeded に 400 を返すと、ずっと送り直されないか。
  - 鍵の入れ替え中に `v1` が複数届く仕様ではないか（決済サービスの仕様しだい）。
- **Nit**：
  - イベント表の掃除がない。
  - `record` の戻り値を使っていない。
  - テストの置き場所。
  - readBody が utf8 にしてから署名を計算している（不正なバイト列は失敗する側に倒れるので害はない）。
- **提案（軽い）**：ルーティングのテストを足す。
- **必須**：なし。

**6. 手順を厚く使うところ**
- **更新と記録の順番**：途中で落ちたらどうなるかを、具体的な値で追う。
- **同じ行を 3 か所が書く件**：注文確定・照合バッチ・Webhook が同じ注文を書く。古い写しで上書きしても、同じ冪等キーなので同じ値に落ち着くことを示す。条件付き UPDATE と比べる。
- **PAYMENT_FAILED の warn**
- **気にしなくてよいもの**：
  - 金額を照らし合わせていない
  - 5 分以内の送り直し
  - has と record の間の競合
- **良い点**：
  - 鍵がなければ受け付けない
  - 生の本文に対して署名を確かめる
  - 失敗の判断を照合バッチに残した
