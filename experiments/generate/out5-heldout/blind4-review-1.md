## 題材 2: feature/reconcile-summary

### 解答キーの要点

- 指摘すべきもの: nit 1 件だけ。ログの `failed`（PAYMENT_FAILED にした＝正常な判定）が「照合に失敗した件数」に読める。本当の失敗は `skipped`
- 問題なし: 例外を握りつぶしていない、障害を「課金なし」と取り違えない、`order` は使い捨てのコピー、save は 1 文、`running` に競合はない（await がない）、`setInterval(async)` の reject は外に漏れない、判定ロジックは main と同じ、失敗し続ける注文が後ろを止めることもない
- 質問: 複数プロセスで動かすか、404 の意味（main からの前提）、ログの出し続け
- 判定: **承認**。must-fix を出したら誤り

自分で確かめた点: 書き換えは findCharge が値を返したあと（38-44 行）だけ。findCharge は 404 なら null、それ以外は
`PaymentUnavailableError`（main の httpGateway.ts:46-47）、タイムアウトは `PaymentTimeoutError`。一覧は
`ORDER BY updated_at`（sqliteOrderRepository.ts:56）。`npm start` は `node src/server.ts` の 1 プロセス。
キーの外で、複数のツアーが挙げた「回が重なったときの lost update」も確かめた。回 A が PAYMENT_FAILED を保存し、
利用者が確定し直して PAID になる。そのあと、5:00 に取った古い一覧を持つ回 B が、findCharge が記録を返す前の
null で PAYMENT_FAILED を全列 upsert すると、PAID を上書きできる。runner はこれを 1 プロセスの中で防いでいる。
コメントの「二重に問い合わせる」より重い理由で、正しい観察と判断した。

### 失敗の型

- **重さの過大評価**: cancellation の K2（設定の `|| 10`）を必須にしたのが B・D・E・F の 4 本。キーは suggestion。「お金に関わる」だけを理由に上げていて、既定のままなら正しく動く点を重さに入れていない
- **良い変更に手当てを足す**: reconcile の A・E が、障害中に break する案をコード付きで提案の筆頭に置いた（F も挙げたが、自分で重さを下げている）。必須ではないので致命的ではないが、キーの「水増ししない」に反する方向
- **見逃し**: cancellation の K3（返金キーの置き場所）は 6 本中 5 本が逃した（拾ったのは F だけ）。reconcile のキーの nit（`failed` の誤読）は 4 本が逃し、A・C・E は隣の `skipped` の二重の意味に留まった。どちらも「既存の流儀やログを読む人の目」で読まないと出ない指摘
- **誤った主張**: cancellation の E。返金キーを「既存の流儀にそろっている」と逆に評価し、CART の同時要求で上書きが「起きうる」とした（同期 I/O の 1 プロセスなので起きない）
- **答えの漏れ**: cancellation の A・B・E・F はタイトルで、A は step 2 の「この表のいちばん上の行を確かめる」でも、予測の問いの前に核心を示している
- **行番号**: 大きな誤りはなかった。cancellation の C で、同じ checkout のコメントが main の行番号（56-58）と head の行番号（63-64）で混ざっている。多くのツアーは「変更なし」のコードを main の行番号で示していて、表示の上では一貫している
- **根拠にリポジトリの外のものを使う**: reconcile の D の「change.diff のハンク」。ジュニアは開けない
- **表示の切れ**: overflow が 21 ステップにある。とくに cancellation の D の step 8（重さの理由が途中で切れる）、C の step 12（照合バッチの場面が読めない）、reconcile の E の step 5 と F の step 6（38 行）、reconcile の B の step 11 と E の step 15（時系列が崩れる）。内容が正しくても、ジュニアには届かない
