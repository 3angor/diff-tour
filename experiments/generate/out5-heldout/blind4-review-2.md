# blind4 ツアー評価（レビュー 2）

評価の進め方: 2 つの題材の差分（`git diff main...feature/<subject>`）と、関係するファイルをブランチごとに行番号付きで読んだ（orderService / gateway / httpGateway / reconcilePendingPayments / sqliteOrderRepository / orderRepository / db.ts / app.ts / server.ts / checkout.ts / 001・002 マイグレーション / テスト / package.json）。採点に使ったツアーの主張は、すべてこのコードで確かめた。解答キーは最低ラインとして扱い、キーにない正しい指摘は加点、誤った指摘や重すぎる重大度は減点した。

## 12 本を通して

### 見えたスタイル
1. **約束を確かめる読み方**（12 本すべての骨格）: コミットメッセージを「確かめる主張」として持ち、差分の外（状態を作る側と片付ける側、SQL の並び順、save の upsert）へ飛ぶ。「確かめた / 読み取れる / シニアの見方」で事実・推測・意見を分け、「問い → 考えてから → 答え」を挟み、最後に「追体験したこと」で締める。
2. **時系列の表で示す型**（oc A・C・D・F、rs A・B・D・E・F）: 2 本の要求を時刻ごとに並べ、失われた更新や上書きを見せる。ジュニアにいちばん効いていた。
3. **修正案を値で確かめ直す型**（oc C・D・F、rs A・C・E・F）: 修正案を同じ場面に当て直し、防げない別案（findCharge を問い合わせる案、PaymentUnavailableError で止める案、3 件で止める案）を退ける。シニアらしい。
4. **締まった版と網羅版**: 15〜16 章の短めのもの（oc B・E、rs C）と、17〜18 章で「気にしなくてよい」表まで網羅するもの（oc A・C・D・F、rs D・E・F）。網羅版は根拠が厚いが、4 ファイルの差分に 18 章はジュニアには重い。

### 失敗のパターン
- **重さを上げすぎる**: oc B・D・E・F が `|| 10` を必須にした（キーは suggestion）。rs A・E は障害時に打ち切る提案を筆頭にし、A は「Chesterton の柵」と呼んで重く見せた。
- **見逃し**: oc の K3（返金キー）は 5 本が逃した（拾ったのは F だけ）。rs の R1（failed という名前）は 4 本が逃した（拾ったのは D・F だけ）。近い「skipped が 2 つの意味」の nit で代わりにしたものが多い。oc B は負の手数料率を見ていない。
- **誤った主張**: oc E が返金キーを「既存の流儀にそろっている」と逆に評価した。oc E が 1 プロセスの Node では起きない CART の競合を「起きうる」と残した。oc A の「PENDING_PAYMENT を確定させるのは照合バッチだけ」（checkout も確定させる）は小さな言いすぎ。
- **答えを先に漏らす**: oc A のツアー題名が全ページで答えを言っている。oc B と E は問いの 1 章前で PENDING_PAYMENT の意味を説明してしまう。
- **行番号と出どころ**: oc C の step 11 は base の行番号で、ほかの章（head の番号）と食い違う。oc D は古い checkout を head の行番号（40-41）で指した。rs D は「change.diff」という、リポジトリにない道具側のファイル名を出した。
- **決まり文句の「問題ない」**: ほとんどない。目立ったのは oc B の「ロックの時間も、この規模なら気にしなくてよい」くらい。ほかの「気にしなくてよい」は、どれも確かめた行を添えている（ここは全体に良くできている）。
- **良い変更に問題を作る**: rs では 6 本とも must-fix を作らず、承認と正しく判定した。作り話の重大問題はなかった。
