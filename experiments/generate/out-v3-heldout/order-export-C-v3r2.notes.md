差分と関係ファイルは読み終えた。いまは下調べの結果を整理して、ツアーの JSON を書いている。



**1. 最初の仮説**
- 経理の月次の突き合わせや問い合わせの担当者が、期間を指定して注文を CSV で取り出せるようにする変更。いままで DB を直接見るしかなかった作業が、管理用の API 1 本で済むようになる、と仮定した。
- コミットは「期間内の注文」と書き、README は「期間内に**更新された**注文」と書いている。言い方がずれているので、確かめる対象にする。

**2. 変更前のコードが守っていた約束（base）**
- `findByStatusUpdatedBefore` の呼び出し元は照合バッチ 1 つだけ（`src/jobs/reconcilePendingPayments.ts:17-20`）。状態と時刻の上限で絞り、`updated_at` の古い順に返す（`src/orders/sqliteOrderRepository.ts:54-59`）。索引は `(status, updated_at)` で、照合バッチのためにある（`db/migrations/001_create_orders.sql:11-12`）。
- `updated_at` は「最後に save した時刻」。`save` が毎回 `now().toISOString()` で上書きする（sqlite:51、InMemory:24）。形式がいつも同じなので、文字列で比べても時刻の順になる。
- 冪等キーは `paymentKeyFor` で必ず作る、という決まりがある（`src/orders/order.ts:13-19`）。
- 金額は円の整数で持つ（migration:4-5）。
- 決済がタイムアウトした注文は PENDING_PAYMENT のまま残る（orderService:56-58）。照合バッチが 10 分以上たったものを 5 分ごとに確定し、そのとき `updated_at` も進む。
- `createApp` は、環境変数がなくても開発用の既定値で起動する（`PAYMENT_API_KEY ?? 'test-key'`、app.ts:11）。
- server は手書きの振り分けで、例外は 500 にしてログに出す（server.ts:14-20）。

**3. 8 つの分野に当てた結果**
1. 約束を守っているか: **兆しあり**。
   - 照合バッチからの呼び出しの意味は変わっていない（条件の順番が入れ替わっただけ）。
   - ただし `updated_at` は「最後の更新」であって「注文した時刻」ではない。月をまたいで照合された注文は翌月の CSV に移る。後で書き出し直すと、過去の月の中身が変わる（orderService:56-58、reconcile:6、sqlite:51）。
2. 失敗したらどうなるか: **兆しあり**。
   - 認可が、通す側に倒れる。`req.token !== deps.adminToken`（head handlers/orderExport.ts:26）は、ADMIN_TOKEN が未設定でヘッダーもないと `undefined !== undefined` が false になり、そのまま通る。
   - 一方、日付の不正は 400、それ以外は 500 になり、ここは筋が通っている。
3. 出したあとどうなるか: **おおむね十分**。マイグレーションはなく、読み取り専用なのですぐ戻せる。ただし漏れたデータは戻せない（2 の問題が重くなる理由）。誰がいつ書き出したかのログはない。
4. 信頼の境界: **兆しあり（2 と同じ箇所）**。
   - 期間の値は正規表現と日付の往復で検証したあとでしか、ファイル名のヘッダーに入らない（reports:23, 28 → handler:47）。ヘッダーへの注入は起きない。
   - SQL は固定の断片をつなぐだけで、値は `?` で渡している。
5. 規模が大きくなったら: **弱い兆し**。状態を指定しない検索では索引 `(status, updated_at)` の先頭の列が効かず、全件を読む見込み。CSV 全体をメモリで組み立て、期間の上限もない。月 1 回の管理用なので、いまは小さい問題。
6. 次に変える人は楽か: **兆しあり**。
   - 「ByStatus」に null を渡し、「Before」に since を足したので、名前と中身がずれた。
   - 呼び出しは `(null, range.to, range.from)` で、引数の順が to → from と逆になっている（reports:77）。
   - reports/handlers の分け方や `paymentKeyFor` の使い回しは、既存の決まりに沿っている。
7. テストは何を証明しているか: **兆しあり**。
   - 認可のテストはいつも `adminToken: 'secret'` で、未設定の場合を試していない（handler test:9）。
   - カンマのテストは、期待値を本体と同じ `toCsvRow` で作っている（orderExport.test:59）。
   - InMemory は並べ替えず、テストは保存した順に頼っている。
8. AI が書いたコードで特に見ること: **兆しなし（範囲内）**。
   - `URL.parse` はリポジトリの外の API なので確かめられない（README は Node 23.6 以降が前提）。
   - 頼まれていない変更は混ざっていない。足りないのは、上の認可の防御。

**4. 重点にした分野**
- 2 と 4 の、認可が通す側に倒れる問題（必須）。漏れたデータは戻せず、テストも捕まえていない。
- 1 の、`updated_at` の意味と経理の目的のずれ（問い）。
- 6 と 7 は提案として短く扱う。
- 気にしなくてよいもの：ヘッダーへの注入、SQL の組み立て、日本時間の固定オフセット（日本に夏時間はない）、500 の扱い、照合バッチの SQL の条件の順番。
- 良い点：期間を半開区間にしたこと、実在しない日付を往復で弾くこと、金額の列名に単位を入れたこと、`paymentKeyFor` を使い回したこと。
