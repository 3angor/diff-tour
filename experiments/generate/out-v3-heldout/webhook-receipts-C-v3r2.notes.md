**1. 最初の仮説**
- 注文確定で決済サービスへの呼び出しがタイムアウトすると、注文は `PENDING_PAYMENT` のまま最大 15 分ほど残る。照合バッチは更新から 10 分たったものだけを見て（base `src/jobs/reconcilePendingPayments.ts:6`）、5 分ごとに動く（base `src/server.ts`）。その間、利用者は 503 で「確認中」と言われ、もう一度確定しても 409 になる。Webhook の `charge.succeeded` を受けて、すぐ `PAID` にする。
- 困らなくなるのは、タイムアウトに当たった購入者。

**2. 変更前のコードが守っている約束（base）**
- `PENDING_PAYMENT` は「課金されたか分からない」という意味（`orderService.ts:56-58`、`gateway.ts:42-43`）。課金されなかったと決められるのは、決済サービスの記録を `findCharge` で確かめる照合バッチだけ（`reconcilePendingPayments.ts:22-31`）。
- 冪等キーは注文ごとに `order-<id>` で、`paymentKeyFor` だけが作る（`order.ts:13-19`）。決済サービスは同じキーの課金を 1 回分として扱う（`gateway.ts:6`）。
- 状態を変えるのは注文確定と照合バッチの 2 か所。どちらも「読む → 外へ問い合わせて待つ → 状態を丸ごと upsert する」形で、条件付きの更新はない（`sqliteOrderRepository.ts:39-52`）。今の約束は手順で守っていて、DB の制約は状態の値の CHECK だけ（`001_create_orders.sql:6`）。
- 層の決まりは README にある。handlers は「HTTP リクエストとの変換」、orders は「業務ロジック」（README `構成`）。既存の `checkout.ts` ハンドラは、例外を HTTP の状態コードに変えるだけ。
- マイグレーションは起動時に番号順に当てる（`db.ts:8-27`）。`DatabaseSync` は同期 API。

**3. 変更と約束の突き合わせ（head）**
- `confirmCharge` が変えるのは `PENDING_PAYMENT→PAID` だけ。`PAID` には触らず、それ以外の状態は warn を出すだけ（`paymentWebhook.ts:64-83`）。「失敗を決めるのは照合バッチ」という約束は守っている。
- 処理の順は「注文を更新してから記録」（`:59-60`）。保存に失敗すると例外が出て 500 になり、記録は残らない（server `:40-43`、テスト `paymentWebhook.test.ts:89-104`）。
- 状態を書く場所が 3 つ目になった。どれも無条件の upsert。
- `has → 処理 → record` は不可分ではない（`:45-60`）。いまは DB の呼び出しが同期なので、処理の途中に別の要求は入らない（推測）。仮に入っても、状態のチェックで 2 回目は何もしない。
- 鍵がなければ 503 を返して閉じる側に倒れる（`:34-37`）。`app.ts` で環境変数から鍵を渡している。

**4. 8 つの分野**
1. 約束: 兆しあり。書き手が 3 つになったのに守り方は手順のまま。`PENDING→PAID` に限ることで約束は守れている。
2. 失敗: 十分な場合に当たる。更新してから記録するのでやり直しが効く。テストもある。
3. 出したあと: 十分な場合に当たる。テーブルを足すだけのマイグレーションで、鍵がなければ 503。古いコードには経路がないので 404 になり、送り直しを待つだけ。
4. 信頼の境界: 十分な場合に当たる。本文を読む前に署名を確かめ、定数時間で比べ、時刻のずれと長さも確かめる。金額は照合しないが、既存のコードも照合していない。
5. 規模: 兆しなし。イベント 1 件につき 1 行で、主キーで引く。表は増え続けるが小さい。
6. 次に変える人: 兆しあり。業務ロジックが handlers/ に入り、`PENDING→PAID` の遷移が 3 か所目になった。`record` の戻り値は使われていない。
7. テスト: 兆しなし（良い）。肝心の行を壊せば落ちる。署名には外で作った値で確かめるテストがある（期待値を本体と同じ計算で作っていない）。重複のテストは注文を人工的に戻している。
8. AI 特有: 小さな兆し。イベント表と「1 回だけ処理する」という言い方が、実際に守っていることより強い。依存は node 標準のみで、`timingSafeEqual` と `createHmac` は node:crypto のもの（リポジトリの外なので確かめられない）。

**5. 厚く語るもの**
- 1（約束）と 2（同時に来たら）を、「本当の守り手は状態のチェックで、イベント表は 2 枚目の守り」という形で語る。もう 1 つは 6（置き場所と重複）。
- 気にしなくてよいもの: 金額の照合、表が増え続けること、マイグレーション、署名の形。
- 良いところ: 閉じる側に倒れる設計、記録の順番、`PAID` を上書きしないこと、接頭辞を共有した逆関数、独立した値でのテスト。
