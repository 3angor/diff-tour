**1. 最初の仮説**
- 経理と問い合わせ対応の担当が、管理用の API から、日本時間で指定した期間の注文を CSV で取れるようになる。管理者だけが呼べ、照合バッチの振る舞いは変わらない、という想定（commits.txt）。

**2. 変更前のコードが守っている約束（base）**
- `findByStatusUpdatedBefore` の呼び出し元は照合バッチ 1 つだけ。「`PENDING_PAYMENT` のまま 10 分以上古い注文」を探す（`src/jobs/reconcilePendingPayments.ts:17-20`）。索引 `(status, updated_at)` はこのためにある（`db/migrations/001_create_orders.sql:11-12`）。
- `updated_at` は「最後に save した時刻」。save のたびに上書きされる（`src/orders/sqliteOrderRepository.ts:39-51`）。作成日時や支払日時の列はない（migration 001）。
- `PAID` は今のコードでは終わりの状態。checkout は `CART` と `PAYMENT_FAILED` しか受け付けず（`orderService.ts:33`）、照合バッチは `PENDING_PAYMENT` しか触らない。
- 金額は円の整数で持つ（migration のコメント）。
- 設定値は `createApp` で環境変数から読み、未設定なら既定値を入れる（`app.ts:7-12`）。
- 変更前のサーバは checkout 以外の要求に 404 を返す（`server.ts:9-13`）。
- 既存のテストは照合バッチの振る舞いを守っている（`test/reconcilePendingPayments.test.ts`）。

**3–4. 8 つの分野を当てた結果**
1. **約束を守っているか — 兆しあり。**
   - 照合バッチのクエリは、条件の順番が変わっただけで意味は同じ。params も conditions と同じ順に積んでいる（head `sqliteOrderRepository.ts:55-67`）。
   - ただし、メソッド名の「ByStatus」「Before」が中身と合わなくなった。
   - 書き出しの軸は `updated_at`（最後の更新）で、「注文日」でも「支払日」でもない。
2. **失敗したらどうなるか — 兆しあり。**
   - `ADMIN_TOKEN` が未設定のとき、ヘッダーのない要求は `undefined !== undefined` が false になり、認可を通る（head `handlers/orderExport.ts:26`、`app.ts:15`、`server.ts:16`）。止める側ではなく、通す側に倒れている。
   - 日付の誤りは 400、それ以外の例外は 500 になる（fact）。
3. **出したあとどうなるか — 十分な場合に当たる。** 読み取り専用で、新しいエンドポイントを足しただけなので戻せる。README も更新されている。ただし本番に `ADMIN_TOKEN` を設定することが前提になる。
4. **信頼の境界 — 兆しあり（最重要）。**
   - 問題は上の fail-open。
   - `filename` に入れる from/to は、正規表現と日付の往復の検証を通ったあとにしか使われないので、ヘッダーの注入はできない（head `reports/orderExport.ts:23`、`handlers/orderExport.ts:34,47`）。
   - SQL は条件を定数の文字列だけで組み、値は bind しているので注入の経路はない。
5. **規模が大きくなったら — ほぼ十分。** status を指定しない検索は索引 `(status, updated_at)` の先頭の列を使えないので、表を全部走査する可能性がある（inferred）。期間に上限がなく、結果は全部メモリに載せる。管理者が月に数回呼ぶ規模なら、今は問題にならない。
6. **次に変える人は楽か — 兆しあり。** お金に関わる照合バッチのメソッドに、`null` と `since` を足して共有した。バッチと書き出しは変わる理由が違う。型の上では、バッチに `null` を渡せるようになった。
7. **テストは何を証明しているか — 兆しあり。**
   - 境界のテストは良い（`test/orderExport.test.ts:33-50`）。
   - 引用符のテストは、期待値を本体と同じ `toCsvRow` で作っているので、`csvField` を壊しても落ちない（同 `:52-60`）。
   - `adminToken` が未設定の場合のテストがない（`test/orderExportHandler.test.ts:6-10,22-26`）。
8. **AI が書いたコードで特に見ること — 兆しなし。**
   - `URL.parse` はリポジトリの外のもので、確かめられない（README は Node 23.6 以降を前提にしている）。
   - 頼まれていない抽象や関係のない変更はない。新しい `RawHttpResult` 型は、ヘッダーを返す必要があるので妥当。

**5. ツアーで厚く扱うもの**
- **必須:** fail-open の認可（分野 4・2）。管理用の口から全顧客の注文が漏れる。止めたときの損害は「管理者が CSV を取れない」だけで小さく、誤って通したときの損害は大きい。
- **提案:** リポジトリのメソッドの共有（分野 6・1）。
- **提案:** 自分の答えを写しているテスト（分野 7）。
- **問い:** `updated_at` を軸にしてよいか（分野 1）。
- **良い点:**
  - 日本時間の日付を半開区間に変え、実在しない日付は往復の比較で弾く。
  - 境界の値を突いたテストがある。
  - filename に入れる値を事前に検証している。
  - 値を bind している。
- **気にしなくてよいもの:**
  - 全表走査とメモリ（件数が小さく、管理者しか呼ばない）。
  - 動的な SQL（注入の経路がない）。
  - 日本の夏時間（日本にはない）。
  - タイミング攻撃（Nit）。
