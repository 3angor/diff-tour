## 題材 2: feature/payment-outage-status（おおむね良い変更）

控えの要点: 仕込んだ問題は 1 つだけ。**status 0 の `PaymentUnavailableError` は `httpGateway.ts:63-68` がタイムアウト以外の fetch の例外をすべてまとめたもので、送信後の切断（ECONNRESET / UND_ERR_SOCKET）も含む。
それを PAYMENT_FAILED にすると照合バッチの対象から外れ、課金済みなのに失敗のまま残る。24 時間を過ぎてやり直すと二重課金になる**（must-fix）。
テストは「待ち受けのないポート」と 503 しか試していない。疑わしいが問題ない点 A は「5xx / 429 は gateway.ts:31 が明記しており、この変更の範囲では問題ないと言ってよい。質問するのは良いが、本題は status 0」。

**4 本に共通する傾向:** 4 本とも 5xx（500 / 502 / 504）が課金済みかもしれない、を本題に据え、status 0 の中身は脇に置いている。
そのうえで、base の orderService.ts:56 のコメント（「決済サービスの障害やタイムアウトでは課金されたか分からない」）と gateway.ts:31 が食い違っていたことを 4 本とも見つけ、
「変更は gateway.ts の側を採った」と指摘している。これはリポジトリの中の事実で、5xx を問いとして出す十分な根拠になる良い発見。ただし控えの基準では、5xx を必須にするのは重さの言い過ぎで、
本題（status 0 は**こちらのコードの都合で作った値**で、リポジトリの中だけで確かめられる）の扱いが薄い。B と D は「送信後の切断が status 0 に入るかは fetch の実装しだいで、このリポジトリでは確かめられない」と書いている。
しかし、変更が足した `httpGateway.test.ts` と同じ作り（リクエストを受け取ってから接続を切るローカルのサーバー）を使えば手元で確かめられる。「確かめられない」は誠実ではあるが、確かめる手間を惜しんでいる。

影響の連鎖（照合バッチは PENDING_PAYMENT しか見ない、冪等キーは 24 時間、「cannot double charge」は 24 時間以内でしか成り立たない、503 の経路にはログがない）は 4 本とも正確に追えている。
B（同じキーでやり直す）、C（タイムアウトは従来どおり）、D（応答の形の変化は問い）も 4 本とも扱っている。E（テストのポート）を明示的に「問題ない」と外した本はない（A・B・C・D とも本物の HTTP サーバーを良い点として挙げるにとどまる）。

## 8 本を通して見える書き方の違い

骨組みは 8 本とも同じ（対象 → 何のための変更か → 地図 → 仕組み → 手が止まる → まとめ → 追体験）。「確かめた／読み取れる／シニアの見方」の札、予想させる問い、修正案を値で確かめる手順、「気にしなくてよいもの」の表もそろっている。違いは次の点にある。

1. **約束の仮説から崩す型**（shipping A・B・D、payment A・B・D）: 第 2 章で「約束 A / B」や「この 1 文が正しいかで安全性が決まる」と仮説を立て、後の問いでそれを崩す。
   - 強み: 問いに必然性があり、ジュニアが「何を確かめるために読むのか」を持てる。B の「書かれていない約束も仮説に入れる」は、問題 2 を見つけるための見方そのものを教えている。
   - 弱み: 仮説を表題や伏線で強く言いすぎると、答えが先に漏れる（shipping A・B の表題）。
2. **問いの形の表題で、短く進む型**（shipping C、payment C）: 表題を問いにして答えを漏らさない。payment C は 16 step で最も短い。
   - 強み: 読み切りやすい。
   - 弱み: 良い点や気にしなくてよいものの説明が薄くなり、判断が厳しい側に倒れやすい（payment C の「悪くしている」）。
3. **選ばなかった設計と比べる段**（shipping B・C、payment B・C・D）: 別案の得失を値で比べる。payment D の 3 案の表、shipping C の条件付き UPDATE がよい例。
   - 強み: 「なぜこの直し方か」が残る。
   - 弱み: 長くなる。payment B の新しい状態を足す案のように、本題から離れて重くなることもある。
4. **名前で覚えさせる**: parse, don't validate（shipping A・C）、mass assignment（4 本とも）、ミューテーションテスト（shipping A）、Chesterton の柵（payment A）。覚えやすさには効いている。
   名前を出す前に値で見せており、名前だけを並べた説明にはなっていない。

## 失敗の型

- **重さの言い過ぎ（おおむね良い変更に対して）**: payment の B・C・D が、外部の仕様しだいの 5xx を必須にした。C は修正案で変更をほぼ取り消し、「全体として悪くしている」とまで言った。
  A だけが「問い（答えが出るまでマージしない）」にとどめた。
- **確かめられるのに「確かめられない」と書く**: payment B・D は、送信後の切断が status 0 になるかを「fetch の実装しだい」で止めた。変更が足したテストの道具（ローカルのサーバー）で数行で確かめられ、確かめていれば本題の重さが変わった。
  4 本とも、本題が「こちらのコードの catch がすべてをまとめている」という**リポジトリの中の事実**だと気付き切れていない。
- **見逃し（浅い扱い）**: payment A・B の status 0 は表の 1 行だけ。疑わしいが問題ない点 E（テストのポートが衝突しない）を明示的に外した本はない。shipping A は JSON.parse の安全性に触れていない。
- **答えの漏れ**: shipping B の表題「早すぎる『決済中』」は問題 2 の答えそのもの。shipping A の表題「約束が 2 か所破れている」は数を先に言う。shipping B の step 6 の伏線も、問題 1 の答えに近い。
  payment の表題（「『課金されていない』を誰が保証しているか」）は前提を疑えという方向づけで、答えまでは言っていないので許容範囲。
- **誤った行番号**: shipping D のテストの行番号（14〜18 → 正しくは 23〜27、20〜28 → 29〜37）。shipping A の server.ts 11〜21 も少しずれる。内容は正しい。
- **技術的に不正確な小さい主張**: shipping C の同時実行（単一プロセスでは窓は無い）、shipping B の「SQLite では ALTER で CHECK を足せない」。
- **埋め草・一般論**: payment C の「件数による負荷も関係ない」。shipping A・D の「AI のコードは型どおりに見えやすい」、shipping B の「AI の書くテストは通ることだけを確かめていることがある」は、この差分の根拠に結びついていない。
  8 本とも末尾に「追体験したこと」の箇条書きがあり、覚えるのには役立つが、前の章の要約と重なる。
- **長さ**: 15〜20 step、1 本あたり約 50KB。shipping C（20 step）と payment B（18 step）は、ジュニアが 1 回で読むには長い。
- **作り話の重大な問題**: 無い。shipping の「id で別の注文を上書きする」は控えにないが、実際に起きる正しい指摘。
