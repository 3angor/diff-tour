## 8 本を通して見えた型

8 本とも骨組みは同じ（対象 → 何のための変更か → 地図 → 仕組み → 手が止まる → まとめ → 追体験したこと）。「確かめた／読み取れる／シニアの見方」の札と、「考えてから → で次へ」の問いがある。その中に、次の型が見えた。

1. **約束を仮説にして検証する型**（shipping の A・B・D、payment の A・D）: 冒頭で「この変更が守るべき 2 つの約束」を言葉にし、各章でそれを崩しにいく。強みは、ジュニアが「何を確かめるために読むのか」を最後まで見失わないこと。とくに B（shipping）の「書かれていない約束（客が立ち直れること）も仮説に入れる」は教育的価値が高い。弱みは、仮説の言い方がタイトルや見出しに漏れて、問いの答えを先に言ってしまいやすいこと（shipping B、payment A・D）
2. **選ばなかった設計と比べる型**（payment の B・C・D、shipping の B・C）: 修正案のほかに別案と代償を表にする。強みは「なぜこの直し方か」が残ること。payment D の案 B、C の照合を早める案は実務的。弱みは、手順が増えて長くなることと、別案の説明に小さな誤り（B の SQLite の CHECK）や中身のない一文（C の「負荷も関係ない」）が混ざりやすいこと
3. **修正案を値で確かめる型**（全 8 本）: 修正案を書いたら、空のメモ、出す前の PAID の注文、片方だけ直した場合などで再確認する。強みは修正案の質が上がること（shipping D の、確認を状態チェックより後に置く理由）。弱みは、確かめた結果として「防げない」と誤って結論することがある（payment A の status 0）
4. **「気にしなくてよい」を表で退ける型**（shipping の B・D、payment の B・D）: 場所付きで退けるので、ジュニアが「全部危ない」と思い込むのを防げる。ただし payment では 4 本とも、控えが「問題ない」とする 5xx を退けられなかった

## 失敗の型

- **重さの上げすぎ（よく効いている変更を止める）**: payment の 4 本すべて。`gateway.ts:31` が明記している 5xx の約束を「コメント 1 行にすぎない」として必須（B・C・D）か、マージ前の問い（A）にしている。「おおむね良い変更」と言い切り、なぜ良いのかを中心に据えたツアーはなかった。題材の中でいちばん大きな共通の弱点
- **本題の取り逃し・切り分けの浅さ**: status 0 が「決済サービスの約束」ではなく「httpGateway の catch がまとめて作る値」だ、という切り分けを、どのツアーも主張の中心にしていない。A は status 0 を「防げない」と誤って結論した
- **ありそうにない懸念を残す**: shipping C の同時実行（同期の SQLite で I/O の待ちがないのに「窓は小さい」）
- **行番号の誤り**: shipping D（orderDetails.test.ts の 2 か所）
- **小さな事実の誤り**: shipping B（「SQLite では ALTER で CHECK を足せない」）
- **答えの先出し**: shipping B のタイトル、payment A の step 2、payment D のタイトル（軽い）
- **中身のない一文**: payment C step 14「件数による負荷も 1 件ずつの処理なので関係ない」
- **長さ**: shipping C（20 手順）、payment B（18 手順）は、重さの低い手順（本文上限の 1 手順、仮定の変更の問い）が混ざっている
- **作り話の問題**: 8 本ともなし。shipping では、控えにない正しい指摘（id の上書き、PII の読み出し、出す順番との組み合わせ）がむしろ多い
- **一般論の「大丈夫」**: ほぼない。「気にしなくてよい」には、ほとんど行番号か仕組みの根拠が付いている（良い傾向）
